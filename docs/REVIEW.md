# 可靠性修改的本地复审

日期：2026-10-29（Asia/Shanghai）。范围：当前未发布的可靠性 Diff、测试与 CI 配置。这是开发过程中的源码自审与回归验证，不是第三方独立审计；仍建议由其他审查者复核代码。

## 发现并补充修复

### P1：POSIX 清理不能只等待直接子进程

此前发送进程组终止信号后，仅等待内部启动进程退出便可能释放清理租约。直接子进程退出不等于所有派生进程已停止，恢复者可能过早取得工作区。

现将 POSIX 清理收敛条件改为整个受控进程组不再有运行成员。Linux 读取 `/proc` 中的进程组及状态，排除已退出的僵尸；其他 POSIX 保守等待组消失。超时或检查失败保留 uncertain 标记，不按成功清理处理。

回归：`test_posix_cleanup_waits_for_remaining_group_members`、`test_posix_cleanup_failure_is_not_reported_as_success`。这些测试在 Windows 模拟信号和组状态，不代表 Linux 实测；真正运行的进程树实验仍需要 Ubuntu CI。

### P1：监督进程异常应保持阻断语义

此前监督协议缺失或返回损坏可能抛普通 RuntimeError，使服务层标记不可恢复的 failed，而不是标记执行结果不确定。同步读取协议也缺少明确的等待上限。

现增加带超时的协议读取，将握手失败、结果缺失、损坏结果和管道异常归为 UncertainExecution。清理未确认时仍保留标记；显式重试不能绕过该标记。

回归覆盖三种异常协议，并在真实监督进程完成测试后注入“清理确认失败”：任务变为 blocked，标记保留，再次授权重试仍阻断。

## CI 配置与结果边界

[ci.yml](../.github/workflows/ci.yml) 在 push、pull_request 和手动触发时运行：

| 作业 | 覆盖 |
|---|---|
| Ubuntu × Python 3.12/3.14 | 静态检查、全量 pytest、实际进程恢复评测 |
| Windows × Python 3.12/3.14 | 相同后端检查，覆盖 Windows Job Object |
| Ubuntu 浏览器 | Chromium、独立服务、11 项页面回归 |

所有作业保留报告，失败时也上传已生成的构件；不配置模型密钥、不调用真实模型。安装依赖遵循 uv.lock。取消 CI 会终止该次 runner，不能据此宣称完成了应用级优雅清理。

本机没有可用 WSL 发行版或 Docker，未运行真实 Linux 验证。只有对应提交的 Actions 作业实际通过，才可以将 Linux 标记为已验证。未通过前不得使用绿色徽章或文档文字暗示已通过。

## 仍存在的限制

- 这是本机可信代码执行模式，不具备 OS 安全隔离。
- 外部不协作写入仍存在 TOCTOU，工作区必须独占。
- 进程组逃逸等对抗行为不在清理保证内。
- 清理不确定标记需要人工核实，不会自动删除。
- 真实模型修复能力、资源配额、断电恢复和分布式执行未验证。

## 独立复核重点

建议审查者在 Linux 运行完整测试，另外检查监督进程同时死亡、进程组检查权限失败，以及失效验收证据是否可能被重用。已有回归不能证明所有任意指令边界均具备相同恢复语义。
