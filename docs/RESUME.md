# 简历与面试准备

## 项目名称

**Deep Agents Workbench：支持故障恢复的代码修复任务服务（基于开源框架二次开发）**

技术栈：Python、Deep Agents、LangGraph、FastAPI、SQLite、SSE、pytest。

## 完成并理解后可使用的描述

- 基于 Deep Agents 与 FastAPI 开发代码修复任务服务，实现任务提交、执行状态查询、SSE 事件补读及修复结果查看；通过独立工作区与跨进程文件锁避免同任务并发执行。
- 围绕工具执行与图 Checkpoint 之间的故障窗口，设计持久化执行意图和结果日志；针对文件编辑使用原始/目标哈希对账，支持重复调用结果复用与外部修改冲突保护。
- 构建独立 worker 进程的故障注入验证，覆盖意图提交后、文件修改后、成功记账后与图完成后等退出窗口，并验证非空测试通过、最终工作区一致性与文件修改次数。

具体测试数量以 `VALIDATION.md` 和当前测试输出为准。不要把此 fixture 的结果写成通用 Agent 成功率、线上业务指标或 SWE-bench 成绩。

## 不能写成个人原创的部分

- Deep Agents/LangChain 的 Agent Loop、上游默认工具和上下文摘要。
- LangGraph 的执行图、持久 Checkpoint 和恢复机制。
- 模型本身的编程能力。

## 当前还缺少的求职材料

- 真实模型下至少一批可公开的固定修复任务，使用隔离环境运行。
- 原版/应用基线与改进版本的公平对照，使用相同模型、任务、预算和超时。
- 两三分钟演示视频：正常修复、故障恢复、外部修改导致阻断。
- 自己画的架构图与至少三个失败案例分析。

建议先选择一个改进方向继续独立完成：

1. **容器执行后端**：为不可信仓库提供受限网络、资源配额和工作区挂载。
2. **上下文预算策略**：保留问题约束/未完成步骤/测试结果，对比默认策略的任务完成率与真实 Token 用量。
3. **评测扩展**：增加真实小项目、不同故障任务和模型，固定 fixture 与测试，输出可复查的原始执行记录。

## 必须能回答的问题

1. Checkpoint 已经能恢复了，为什么还需要工具执行日志？
2. 文件写完但记账前崩溃，怎样判断是否重复执行？
3. 外部修改和 Agent 修改冲突时，为什么不能直接覆盖？
4. 为什么测试执行结果未知时不能随便重跑？
5. 两个服务进程同时恢复一个任务会怎样？
6. 模型说“完成”为什么不等于任务成功？
7. 零测试为什么也可能返回退出码 0？
8. 工作区路径限制与操作系统沙箱有什么区别？
9. fixture 模型验证了什么，没有验证什么？
10. 你要怎样设计真实模型的基线对照，避免把随机波动当成提升？
